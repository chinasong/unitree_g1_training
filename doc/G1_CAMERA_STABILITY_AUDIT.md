## 定位与改动

D435i 枚举在 USB 3（5000 Mb/s），官方视频服务存活；检查时近十分钟内核日志未发现相机断连记录。超时期间，独立被动订阅在 30 秒内看到了 43 个请求对应的 43 个成功响应。故不能用 SDK_3104 单独断言相机或 USB 故障。探针的到达时间来自轮询，不能当作真实网络时延。

| 对照 | 实测 | 结论范围 |
| --- | --- | --- |
| 原 SDK 回调接收器，约 60 秒 | 61 次状态采样：58 次 stale / SDK_3104、3 次 live | 复现故障；状态采样次数不是 RPC 次数 |
| 同进程改成轮询，180 秒 | 487 次 RPC，424 次成功、63 次超时 | 仅替换回调接收还不足以解决 |
| 独立进程协议探针，60 秒 | 300/300 成功，最大请求用时 21.1 ms | 同期原接收进程仍超时，支持进程接收链路干扰判断 |
| 独立进程＋解码＋IPC＋Mac HTTP，180 秒 | **899/899 次成功、0 超时；37/37 张不同 JPEG** | 完整链路在本窗口内有效 |

三分钟窗口：**2026-10-21 12:48:31–12:51:31 北京时间**（04:48:31–04:51:31 UTC）。181 次状态采样均为 live，取图请求帧龄最大 309 ms，身体反馈龄最大 54 ms。图像原始 1920×1080，Mac 每次解码为 960×540。请求帧龄不等于传感器曝光延迟，官方未提供曝光时间。

最终发布 `eb94ddc601d9`（基础档案 v13）另做发布后复测：**2026-10-21 12:53:07–12:54:07 北京时间**，300/300 次取图成功、0 超时；61/61 次状态为 live，13/13 张 Mac JPEG 解码成功且哈希不同，取图请求帧龄最大 193 ms、身体反馈龄最大 60 ms。Orin 的 430 个发布文件均通过 SHA256 核对，四个官方服务的 PID、启动时钟及命令行与发布前相同。

当前接收器只使用固定版本官方 IDL / ChannelFactory 与 videohub API 1001。单次请求截止 700 ms，最多一个在途请求，按请求 ID 与 API ID 匹配响应，忽略其他客户端和迟到响应；租约 ID 为 0。通过 `spawn` 启动独立解释器，隔离高频身体 DDS 回调与图像接收，不 fork 现有 DDS 线程。未修改官方 SDK 或服务。

父进程通过单向 IPC 接收已解码帧，保留原始请求时间。工作进程退出清空帧，2 秒无 IPC 更新撤回，服务端与浏览器仍在 1 秒帧龄后隐藏旧图。面板展示近 60 秒成功、超时和失败计数，能直接发现复发。

证据支持本项目进程内接收路径受干扰；**尚未证明具体 GIL、CycloneDDS 原生调度或 SDK 缺陷是唯一根因**。没有调大 DDS/系统网络参数、改相机参数或用长超时掩盖问题。原失败记录保留在基础档案来源中。[固定版本官方错误码定义](https://github.com/unitreerobotics/unitree_sdk2_python/blob/814556d15970dd2ecf1c9984e845ca02ab07e206/unitree_sdk2py/rpc/internal.py)。
